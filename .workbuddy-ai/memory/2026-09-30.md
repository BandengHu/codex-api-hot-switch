# 2026-09-30

## Tauri 版 0.2.12：路径 bug 修复 + 中文安装界面（已提交 6698c9a，分支 tauri/experiment）

### ① 路径 bug 根因（用户实测报错）
`找不到 server.js：\\?\C:\Users\Administrator\AppData\Local\Codex SwitchGate\server`

追到 `tauri-utils-2.10.0/src/platform.rs` 的 `resource_dir_from()`：
**只有 linux / macOS / iOS 三个分支，Windows 走 `cfg!(target_os="windows")` 唯一分支，无条件 `return Ok(exe_dir)`**。
即 `resource_dir()` 在 Windows = exe 同级目录。
而 `bundle.resources = ["resources/server/**/*"]` 安装后会**原样保留 `resources\` 那一层**
→ 真实位置是 `<install>\resources\server\server.js`，原代码只 `join("server")` 所以找不到。

**修复**：候选数组 `[res/resources/server, res/server]`，逐个查 `server.js` 存在性；
全失败时错误信息列出两个尝试路径。

### ② 中文安装界面
- 字段是 `bundle.windows.nsis.languages`，值用 **NSIS 语言代码** `"SimpChinese"`。
- tauri-bundler 2.10.0 内置 `.../windows/nsis/languages/SimpChinese.nsh`（官方完整译文：
  addOrReinstall / alreadyInstalled / chooseMainHowToInstall / createDesktop / uninstallApp…），**不用自己写翻译**。
- `displayLanguageSelector: false` → 直接中文，不弹语言选择框。
- 验证方法：看生成的 `target/release/nsis/x64/installer.nsi` 第 464-467 行
  `!insertmacro MUI_LANGUAGE "SimpChinese"` + `!include "...\SimpChinese.nsh"`。

### ③ NsisConfig 踩坑（连续错两次）
- `NsisConfig` 是 **`deny_unknown_fields`**：任何未知字段让整个对象校验失败，报错只含糊说
  `not valid under any of the schemas listed in the 'anyOf' keyword`，**不指出具体字段**。
  → 改动前先用 `tauri-cli-2.12.0/config.schema.json` 的 `definitions.NsisConfig` 预校验。
- **`compression` 合法值是全小写 `zlib`/`bzip2`/`lzma`/`none`**；PascalCase 的 `"Lzma"` 是非法值
  （我曾误以为要改成 PascalCase，反而更错）。
- `NsisConfig` 合法字段全集：`template` / `headerImage` / `sidebarImage` / `installerIcon` /
  `uninstallerIcon` / `uninstallerHeaderImage` / `installMode` / `languages` / `customLanguageFiles` /
  `displayLanguageSelector` / `compression` / `startMenuFolder` / `installerHooks` / `minimumWebview2Version`。
  **没有 `shortcutName`**（正确字段是 `startMenuFolder`）。

### ④ 新增诊断能力（GUI 无控制台 → 落盘是唯一稳定手段）
- `guide_log(level, message)` 命令 → `logs/guide.log`（引导页各状态节点写日志）
- `debug_paths()` 命令 → JSON：`resourceDir` / `serverRoot` / `serverJsExists` / `exeDir` / `dataDir` / `debugBuild`
- `boot.log` 启动痕迹（`run()` 进函数即写一行 pid + exe + data_dir）→ 定位静默退出死在哪步
- `probe_node_version` 加 **4 秒超时轮询**（原 `Command::output()` 无超时，候选 node 挂网络盘会永久卡住）
- `setup()` 里托盘创建失败**不再 panic**（原 `.expect("创建托盘失败")`），改记 `tauri-shell.log` 继续跑

### ⑤ 体积再降：8.74MB → 4.98MB
- 删 `vendor/.pnpm`（`prunePnpmStore`）。依据：Next standalone 已把依赖 bundle 进 `.next/server/chunks`；
  实测移走后 **16 个 API 路由全 200/405、0 个 5xx**，日志出现

  实测 **146 个条目**绝对路径超 Windows 260 上限（最长 **291**）→ `makensis` 打不开文件即整体 abort。
- **注意 `pruneVendor` 顺序**：先 `pruneDuplicatedTopLevelVendorPackages`（依赖 `.pnpm` 存在），
  再 `prunePnpmStore`。顺序反了会把去重依据删掉。

## 补充（同日稍晚）：查出「装完仍报找不到 server.js」的真正原因

用户装 0.2.12 后仍报同样错误。检查安装目录：
`%LOCALAPPDATA%\Codex SwitchGate\resources\server\` 下**只有 `vendor\` 一层** —— 其余全丢。

### 根因（不在壳代码，在资源准备脚本）
1. 上一轮为测试建的 junction 被递归删除时**穿透删掉了源** `tauri/src-tauri/resources/server` 的内容。
2. 重跑 `prepare-tauri-build.cjs` 时先 `ENOTEMPTY`（残留挡路）、再 `ENOENT`（拷贝中断）。
3. **但最后一次脚本「成功退出」了** —— 它是拿一个残缺目录打出安装包的。

### 铁证
- 那次安装包 **4.98MB**（正常 **8.74MB**）。
- `installer.nsi` 里 `server.js`、`.next/server/app/api` 的 `File` 指令**一条都没有**，
  只有 `resources\server\vendor\...`。
  → **体积明显偏小 + 只有 vendor ≈ 空包**。

### 修复
`assertResourcesComplete(dir)`：打包前逐项核验，不过就抛错中止（不再打印「已就绪」）。
- 必需路径：`server.js` / `.next/BUILD_ID` / `.next/server` / `.next/static` / `package.json`
- `.next/server/app/api` 子项 >= 5
- `.next/server/chunks` 子项 >= 20（正常约 193）

### 重打包过程中的新坑
- **`target/release/nsis` 与 `bundle/nsis` 会被句柄占用**：
  报 `另一个程序正在使用此文件，进程无法访问。 (os error 32)` 或 `EPERM`（rename 时）。
  **解法**：把这两个目录**改名挪走**再重跑（rename 快且不受 safe-delete 阈值限制）。
  编译已缓存时只需 ~40s。
- 别用 `rm -rf` 清这些目录：safe-delete 会拦 9999 个文件，直接 SIGTERM 整个命令。

### 最终验证（这次做了完整的端到端）
新包 **8.74 MiB**，用 7-Zip 解包核对：
- 1487 个文件 / 解压后 48MB
- `resources\server\server.js` ✅、`.next\BUILD_ID` ✅、`.next\required-server-files.json` ✅
- `installer.nsi` 中 `.next\server\app\api` **529 条**、`vendor\tsx` **123 条**

**实跑服务**（从解包目录 `node server.js`）：
```

/                       -> 200
/api/console            -> 200
/api/codex-config       -> 200 (1.5s)
/api/workbuddy-pool     -> 200 (553B)
/api/codex-sessions     -> 200 (5.5s)
/v1/models              -> 200
/api/providers/models   -> 405（GET 不允许，符合预期）
```
0 个 5xx。

### 验证手段（沙箱内也能做，值得记）
- **7-Zip 解包**：`"/c/Program Files/7-Zip/7z.exe" x <安装包> -o<目录> -y`
  NSIS 是 LZMA 压缩，能直接解出真实文件 —— **这是最可靠的端到端校验**。
- 在解包目录直接 `node server.js` 实跑 + 打关键路由。
- **NSIS 静默安装到指定目录不可靠**：`/S /D=<path>` 对含中文+空格的路径会静默失败（无输出）。
- 冷启动并发打路由会超时（前面慢路由未结束就发下一个）→ 要**逐个等结果**或加轮询等 `Ready`。
- 端口有时被抢占报 `ECONNREFUSED` → 换端口重试即可，非内容问题。

## 【重大事故】第一次打包打出了「空包」（已修复，提交 26f13ff）

### 现象
用户装上 0.2.12 后**仍然**报 `找不到 server.js`，错误里列出两个候选路径都对。
检查安装目录 `%LOCALAPPDATA%\Codex SwitchGate\resources\server\`：
**只有 `vendor\` 一层**，`server.js` / `.next` / `app` / `lib` 全部不见。

### 根因链（三个错误叠加）
1. 上一轮为测试建的 **junction 在递归删除时穿透**，把源 `resources/server` 的内容删空了（见坑 ⑧）。
2. 重跑 `prepare-tauri-build.cjs` 时先 `ENOTEMPTY`（残留 node_modules 清不掉）、后 `ENOENT`
   （`fs.cp` 复制时源文件被并行删除）—— 中途失败。
3. **最后一次它却「成功退出」并打印「资源已就绪 82MB」** —— 但那 82MB 是**残缺状态**，
   于是拿它打出了安装包。
- **铁证**：那次包 **4.98MB**（正常 **8.74MB**）；`installer.nsi` 里
  `server.js` / `.next/server/app/api` 的 File 指令**一条都没有**（只有 vendor）。

### 修复
新增 `assertResourcesComplete(dir)` 护栏，打包前逐项核验：
- 必需路径：`server.js` / `.next/BUILD_ID` / `.next/server` / `.next/static` / `package.json`
- `.next/server/app/api` 子项 **>= 5**（否则路由没拷进去）
- `.next/server/chunks` 子项 **>= 20**（正常约 193，过少说明拷贝中断）
不通过直接抛错中止，**不再打印「已就绪」**。

### 重新打包后的验证（这次全部做实）
- 体积 **8.74 MiB**（对比空包 4.98MB）
- `installer.nsi`：`resources\server\.next\server\app\api` **529 条**、`vendor\tsx` **123 条**、
  `server.js` / `BUILD_ID` / `required-server-files` 均在
- **实跑** `node server.js` → `▲ Next.js 16.2.6 ✓ Ready in 0ms`
- **6 个关键路由全绿、0 个 5xx**：`/` 200 (38KB)、`/api/console` 200、`/api/codex-sessions` 200、
  `/v1/models` 200、`/api/workbuddy-pool` 200、`/api/providers/models` 405（GET 不允许，符合预期）

### 教训（必须遵守）
1. **`prepare-tauri-build.cjs` 退出码 0 ≠ 资源完整**。打包前必须独立复核
   （体积、`installer.nsi` 里的条目数、最好实跑一次 `node server.js`）。
2. **体积是强信号**：正常包 **8.74MB**。明显偏小（如 5MB）必然缺文件。
3. **junction 的删除语义**：删链接本身用 `fs.unlinkSync`（不穿透）；**永远不要**对含 junction
   的目录做 `rm -rf` / `fs.rmSync(recursive)`。
4. 清理残留目录时，**改名（rename）比递归删除更安全也更快**，还能绕开 safe-delete 的 50 文件阈值。
   代价是别名目录会残留，需加进 `.gitignore`（本次已加 `.res-old-*/`、`.nsis-stale-*/`、`resources-broken/`）。
